# ADR-001: Worker, AI SDK, and one session Durable Object

**Status:** Accepted  
**Date:** 2026-11-11  
**Requirements:** `Senior AI EngineerCoding Challenge_ Small Enterprise AI Assistant.pdf`  
**Design:** `ARCHITECTURE_DECISIONS.md`

## Context

The assignment needs a local Cloudflare application with exactly three agents, concurrent independent work, sequential dependent work, separate histories and capabilities, a native tool, a real MCP client and server, an on-demand skill, two-dimensional permissions, a React chat, a timestamped trace, and tests. The seven demonstrations use a real model. The implementation budget is about eight hours.

The orchestration has two fixed specialists. The security behavior has to be enforced when a model is helpful, wrong, or following text returned by a tool.

## Decision

Use a plain TypeScript Worker, the Vercel AI SDK on OpenAI Responses (`gpt-6.1-sol`), and one SQLite Durable Object per demo user.

The orchestrator makes one structured plan. Application code validates it and runs it in dependency waves. Specialist calls and the final synthesis are separate model calls. Synthesis has no tools. Outcomes are a closed union rendered by code.

The policy system is a second Worker using `createMcpHandler`, called through a private service binding and a pinned fetch adapter. That is the only use of the Cloudflare Agents SDK.

## Options

### A. Plain Worker, AI SDK, one session object

The scheduler is a short loop: group ready tasks, run the IT chain and the HR chain with `Promise.all`, and pass a typed handoff to the next wave. Authorization, traces, and retries are ordinary functions. Session ownership is `getByName(demoUserId)`.

This is the selected option.

### B. Cloudflare Agents SDK and agents-as-tools

`agentTool()` turns another agent into a tool the parent model can call. Each child has its own Durable Object, messages, and failure record. That satisfies "separate histories" with more machinery.

Concurrency is whatever the parent model emits. Scenario 3 needs overlapping specialist work even when the model does not emit parallel tool calls. Scenario 6 needs HR to receive the reset request and report that it cannot do it. A parent that can see both specialist tools will call the specialist that can succeed. Stopping that substitution means hiding tools or ignoring the model's second choice, which is the same code option A already has.

Agents-as-tools also adds child run state, WebSocket replay, and cleanup the PDF does not require. The permission intersection, the trace, the skill loader, and the MCP allowlist would still be application code.

`createMcpHandler` remains in use because it is the supported stateless MCP server on Workers. `McpAgent` is deprecated. Using the handler does not mean the orchestrator should be an Agents chat class.

### C. LangGraph or Cloudflare Workflows

A graph library would wrap the same two specialists in another runtime and another persistence story. Cloudflare Workflows are for durable multi-step jobs. This turn is one HTTP request. A workflow retry of a step that inserts the simulated reset can create a second row unless every step rediscovers the idempotency rule. That is extra surface for a bug the in-request transaction already closes.

Whether LangGraph runs comfortably inside a Worker was not treated as a reason to reject it. The reason is the extra runtime for a two-node wave loop.

## Why one object per demo user

Cloudflare's guidance is to name a Durable Object after the logical entity with `getByName`, and to use `newUniqueId` only when the id must be stored somewhere else. Here the entity is the demo user's active session. The three names are the fixture ids. The client never submits an object id, so a missing ownership check cannot attach Alex's request to Jordan's object.

A server-issued conversation id is the right model when one person has many chats. This assignment has one active session per selected demo identity. Random ids would need client storage, a 403 path, and a refresh story the PDF marks optional. They are safer only against someone who can set the demo header and does not know the other user's conversation id. The PDF's switcher is that header.

Concurrent requests, stale writes, and separate agent histories are properties of the object protocol, not of how the id is minted. Those rules are in `ARCHITECTURE_DECISIONS.md` section 7.

Session reset exists so the seven demonstrations can start from a clean transcript. Traces used in the write-up are exported before a reset.

## Consequences

- Scenario 3 overlap is produced by `Promise.all`, then checked with a barrier test and with real timestamps.
- Scenario 5 never invokes a specialist. Scenario 6 invokes the HR model without the reset tool and does not add an IT task.
- Policy text cannot become IT context except through the typed equipment handoff.
- The MCP identity header is attached only by the pinned fetch adapter. Redirects are not followed.
- `gpt-6.1-sol` planning starts at medium reasoning. Other calls start at low. The planning experiment can lower the plan call. It cannot silently switch models or APIs.
- The design is not a claim that the AI SDK, the service binding, and `createMcpHandler` already work as one path. `docs/FEASIBILITY_PLAN.md` is the gate. `docs/verification.md` stays `NOT TESTED` until runs exist.
